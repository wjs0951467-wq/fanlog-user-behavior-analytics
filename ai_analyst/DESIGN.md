# FANLOG AI 분석가 설계서 v1

## 1. 한 줄 정의
운영 담당자가 한국어로 묻으면, SQL 근거와 계산 가정을 투명하게 보여주며 답하고,
이탈 위험 팬을 찾아 운영 액션을 "검증 가능한 가설"로 제안하는 분석 에이전트.

## 2. 사용자와 대표 시나리오
사용자는 FANLOG 운영/CRM 담당자(SQL을 모르는 사람)다.
- S1 지표 질문: "현재 휴면 팬은 몇 명이야?"
- S2 원인 탐색: "소통 공백이 긴 아티스트는 누구야?"
- S3 위험 세그먼트: "이탈 위험이 높은 팬 중 구매 경험이 있는 팬은 몇 명이야?"
- S4 액션 제안: "이 세그먼트에 보낼 메시지 초안과 효과를 검증하는 방법을 알려줘."

## 3. 설계 원칙 (면접에서 설명할 포인트)
1. 정확성 우선: 모든 숫자는 SQL 실행 결과에서만 나온다. LLM 이 숫자를 직접 만들지 않는다.
2. 투명성: 답변마다 SQL, 계산 가정(assumptions), 시도 이력(attempts)을 함께 돌려준다.
3. 방어 3겹: DB 읽기 전용 계정 / SQL 가드레일 / 연결 옵션(read-only, timeout).
4. 측정 가능성: 사람이 검증한 정답 평가셋과, 기능별 정확도 비교(ablation)를 남긴다.
5. 인과 단정 금지: 액션 제안은 "효과를 약속"하지 않고 "가설 + 검증 방법"으로 쓴다. (README 의 통계 표현 원칙과 동일)
6. LLM 교체 가능: LLM 호출은 app/llm.py 한 곳에만 둔다.

## 4. 응답 계약 (ask 의 반환값, 모든 기능이 이 형식을 따른다)
- question (문자열): 사용자 질문
- sql (문자열 또는 null): 최종 실행에 성공한 SQL(가드레일을 거쳐 LIMIT 이 붙은 형태). 실패/거절이면 null 이고, 실패한 SQL 은 attempts 에서만 볼 수 있다.
- columns, rows, row_count: 실행 결과
- assumptions (문자열 목록): 계산 기준 한국어 1~3줄. 예) "탈퇴 사용자 제외", "데이터의 마지막 날짜 기준"
  모델이 JSON 대신 SQL 블록만 준 경우에는 "모델이 가정을 반환하지 않음" 문구가 들어간다.
- summary (문자열 또는 null): 결과를 한국어 2~3문장으로 해석 (입력에 없는 숫자와 원인 단정 금지).
  0행이면 고정 문구 "조건에 해당하는 데이터가 없습니다." / 요약 호출 실패 또는 요약을 끈 경우 null.
- attempts (목록): SQL 생성 시도마다 {sql, error_type, error_message}. sql 은 모델이 쓴 원본(없으면 null).
  error_type 은 아래 6가지 중 하나다.
  - none: 성공
  - guard: 가드레일 차단 (재시도)
  - db: DB 오류 (SQL 잘못이면 재시도, 접속/인증 오류면 즉시 중단)
  - parse: 응답에서 SQL 을 전혀 찾지 못함 (재시도)
  - false_refusal: 거절했지만 "없다"고 한 테이블/컬럼이 실제로 존재함 (질문당 1회 재시도)
  - refusal: 정상 거절로 인정 (종료). 평가에서 "거절이 정답인 문항"은 마지막 시도가 refusal 인지로 채점한다.
- error (문자열 또는 null): 최종 실패 사유. 거절이면 "CANNOT_ANSWER: 사유", 그 외에는 "[가드레일 차단]", "[DB 오류]", "[출력 형식 오류]", "[거짓 거절]", "[LLM 오류]" 로 시작한다.
- usage: {llm_calls, tokens} 호출 수와 총 토큰 수(입력+출력 합계). 실패한 호출도 llm_calls 에 센다. (공용 크레딧 관리용)
기존 키(question, sql, columns, rows, row_count, error)는 그대로 유지한다.

## 5. 아키텍처
    사용자 질문
      -> app/text2sql.py : ask()  [고정된 파이프라인]
           1) app/llm.py  : SQL 생성 (JSON 으로 sql + assumptions, 또는 거절 cannot_answer + missing 반환)
           2) app/sql_guard.py : 검증 (SELECT 1문장, 허용 테이블, 금지 함수, LIMIT 강제)
           3) app/db.py   : 읽기 전용 실행
           4) 실패하면 에러를 모델에게 돌려 재시도 (최대 3회)
           5) app/llm.py  : 결과 요약
      -> app/churn.py : 이탈 위험 점수와 세그먼트 (Day 3)
      -> app/agent.py : 도구 호출 에이전트 (Day 4). ask / churn / 액션 추천을 도구로 묶는다.
      -> UI (Day 4)
핵심 결정: SQL 생성은 에이전트가 자유롭게 하지 않고, 검증된 ask() 파이프라인을 "도구"로 재사용한다.
(에이전트가 가드레일을 우회할 길을 만들지 않기 위해서)

## 6. 일정별 상세

### Day 2 (11/12) - 스스로 고치고, 가정을 설명하는 Text-to-SQL
구현 범위:
1. app/llm.py: complete(system, messages, json_mode=False) 한 함수에 OpenAI 호출을 모은다. 키/모델은 환경변수.
   반환값은 {"text", "tokens"}. json_mode=True 면 OpenAI 의 response_format=json_object 를 쓴다.
   이 모드는 프롬프트에 "JSON" 이라는 단어가 없으면 400 에러가 나므로, 호출 전에 코드가 먼저 확인한다.
2. LLM 출력 형식(JSON 객체):
   - 답할 수 있을 때: {"sql": "...", "assumptions": ["..."]}
   - 답할 수 없을 때: {"sql": null, "cannot_answer": "사유", "missing": ["테이블" 또는 "테이블.컬럼", ...]}
   JSON 파싱에 실패하면 기존 ```sql 블록 추출로 대체(fallback)한다. SQL 을 건졌으면 재시도 없이 진행하고
   assumptions 에 "모델이 가정을 반환하지 않음"을 넣는다. SQL 을 전혀 건지지 못했을 때만 parse 로 기록하고 재시도한다.
3. 재시도 루프(SQL 생성 호출 최대 3회). 재시도 대상: 가드레일 차단, SQL 잘못인 DB 오류, 파싱 실패, 거짓 거절.
   - DB 오류는 PostgreSQL 오류 코드(SQLSTATE)로 구분한다. 42xxx(문법, 없는 테이블/컬럼), 22xxx(데이터 오류), 57014(타임아웃)만 재시도한다.
     접속/인증 오류 등 그 외는 SQL 잘못이 아니므로 에러 원문을 모델에게 보내지 않고 즉시 중단한다.
   - LLM API 자체의 오류(인증, 한도 등)도 재시도하지 않고 "[LLM 오류]" 로 끝낸다.
   - 재시도는 시스템 프롬프트를 그대로 두고 대화에 [이전 응답, 에러 피드백]을 누적한다.
     피드백에는 "이전 SQL + 에러 원문(HINT 줄 포함, 최대 500자) + 같은 실수를 반복하지 말 것"을 넣는다.
     (앞부분이 매번 같아 프롬프트 캐싱이 적용되고, 3번째 시도가 1번째 실수로 되돌아가지 않는다.)
   - 0행 결과는 에러가 아니다. 재시도하지 않고 summary 에 고정 문구 "조건에 해당하는 데이터가 없습니다."를 넣는다(요약 LLM 호출 없음).
     (무한 재시도 방지와, 모델이 조건을 억지로 바꿔 틀린 답을 만드는 것을 막기 위한 의도적 결정)
4. 거짓 거절 교정: 거절 응답의 missing 목록을 허용 테이블 15개의 schema_profile.json 과 대조한다.
   "테이블" 또는 "테이블.컬럼" 중 하나라도 실제로 존재하면 거짓 거절로 보고, 존재한다는 근거(컬럼 목록)를 돌려주며 질문당 1회 재시도한다.
   어디에도 해당하지 않는 이름이거나(허용되지 않은 meta_generation_run 포함) missing 이 비어 있으면 정상 거절(refusal)로 인정한다.
   교정 후에도 다시 거절하면 정상 거절로 끝낸다.
5. 요약 단계: 별도 호출(일반 텍스트). 입력은 질문 + assumptions + 컬럼 + 전체 행 수 + 상위 20행.
   "입력에 없는 숫자를 쓰지 말 것, 원인을 단정하지 말 것"을 프롬프트에 명시한다.
   요약 호출이 실패해도 결과는 살리고 summary 만 null 로 둔다. ask(question, summarize_result=False) 로 요약을 끌 수 있다(평가용).
6. usage 기록: 질문 1개당 llm_calls 와 총 토큰 수를 결과에 포함한다. 질문당 호출은 최대 4회(SQL 3 + 요약 1)로 제한한다.
테스트(pytest, LLM/DB/프로파일은 mock): 정상 1회 성공 / 1회 실패 후 성공 / 3회 모두 실패 / 거짓 거절 교정 / 정상 거절 인정 / 0행 처리 / 기존 sql_guard 23개 통과
  + fallback 진행 / SQL 없음 parse 재시도 / 재시도 메시지 내용 / 접속 오류 즉시 중단 / meta_generation_run 거절 인정 / 교정 후 재거절 종료 / 호출 상한과 usage 합산 / 요약 실패 시 결과 유지 / llm.py(모델 환경변수, json_mode).
완료 기준: pytest 전부 통과. eval_notes.md 의 6개 질문이 모두 기대값과 일치(탈퇴자 제외 기준). CLI python -m app.text2sql "질문" 이 계속 동작.

### Day 3 (11/13) - 이탈 위험 점수와 세그먼트 (app/churn.py)
LLM 을 호출하지 않는다(OpenAI 호출 0회). 아래는 최종 구현 기준이다.
- 원 프로젝트와의 관계: 원 프로젝트 PRD 는 "머신러닝 기반 이탈 예측"을 범위 밖으로 두었다. 이 작업은 PRD 를 바꾸지 않고, 확장 프로젝트(ai_analyst)에서 따로 다루는 실험이다.
- 예측 문제: 기준일 t 에 active 인 팬이 t+1 ~ t+14일 동안 핵심 활동을 한 번도 하지 않는가(churn_14d = 1).
  = "지금 활동 중인 팬이 14일 뒤 이탈 위험(at_risk) 상태로 넘어가는가". 특징은 t 이하, 라벨은 t 이후 정보만 쓴다.
- 모집단(기준일마다): 그날 active / 탈퇴자(is_deleted) 29명 제외 / 가입 14일 미만 제외.
  이미 at_risk, dormant 인 팬은 "계속 비활동인가"라는 다른 질문이 되므로 넣지 않는다.
- 기준일: 01-15 부터 7일 간격 9개. 학습 01-15, 01-22, 01-29, 02-05, 02-12(5,911행, 양성 323) /
  버림 02-19(학습 라벨이 평가 구간을 미리 보지 않도록 14일 간격) / 평가 02-26, 03-05, 03-12(4,286행, 양성 168).
  시간순 분할이며 무작위 분할을 하지 않는다. 03-17 이후 기준일은 정답(이후 14일)을 알 수 없어 쓰지 않는다.
- 데이터 로딩: 코드에 고정한 SELECT 5개를 validate_sql(sql, max_rows=200000) 로 통과시킨다. sql_guard.py 와 db.py 는 수정하지 않았다.
  팔로우와 구독은 "지금 상태"가 아니라 기준일 시점으로 다시 계산한다.
- 특징: 활동 기반 5개(마지막 핵심 활동 후 일수, 최근 7일/14일 활동일수, 직전 주 대비 변화, 최근 14일 구매),
  관계 3개(팔로우 수, 팔로우 없음 표시, 구독 여부), 소통 공백 2개(팔로우 중인 아티스트의 소통 공백 최솟값, 팔로우 없음 표시).
- 모델 4개. 대표 성능은 M1 이고, M2/M3 는 "특징을 추가했을 때 달라지는가"를 보는 비교다.
  - M0 규칙 기준선: 마지막 핵심 활동 후 일수가 긴 순서 (모집단이 active 뿐이라 "at_risk 인가"는 기준선이 될 수 없다)
  - M1 주 모델: 로지스틱 회귀, 활동 기반 특징만
  - M2: M1 + 관계 특징 / M3: M1 + 소통 공백 특징 (README 가설 H-02 와 연결되는 비교)
  - 표준화는 학습 구간 통계로만 한다. 정규화 강도 C 는 1.0 으로 고정하고 평가 결과를 보고 조정하지 않는다. class_weight 는 쓰지 않는다.
- 지표: 기준일별 AUC 의 평균이 주 지표(합친 AUC 는 날짜 효과가 섞여 참고용), PR-AUC, 기준일별 precision@100 과 그 기준일 양성 비율 대비 배수(lift).
  95% 신뢰구간은 사용자 단위 부트스트랩 1,000회(같은 사용자가 여러 기준일에 나오므로 행이 아니라 사용자를 뽑는다).
- 결과(평가 구간): 평균 AUC M0 0.591 / M1 0.650 / M2 0.638 / M3 0.640, lift@100 평균 M0 1.91 / M1 2.02 / M2 1.51 / M3 1.29.
  M1 - M0 의 평균 AUC 차이 구간은 +0.019 ~ +0.101 로 0 을 포함하지 않지만, lift 차이 구간은 -0.47 ~ +0.65 로 0 을 포함한다.
  M2 는 M1 보다 나아지지 않았다. M3 는 평가 구간에서 소통 공백 값이 0 과 1 뿐이라 "이 구간에서는 검증 불가"다("효과 없음"이 아니다).
- 위험 군: 점수 순위로 "상위 10%군 / 11~30%군 / 나머지"로 나눈다. 10% 와 20% 는 데이터 근거가 없는 운영 가정이다.
  "고/중/저위험"이라는 이름은 쓰지 않는다(M1 의 최대 예측 확률이 17% 수준이라 실제보다 강한 인상을 준다).
  평가 구간의 군별 실제 비율: 상위 10%군 7.5%(전체 대비 1.90배) / 11~30%군 5.3%(1.34배) / 나머지 3.0%(0.77배).
  탐색적 추가로 M0 으로 같은 비율의 군을 나눠 비교했고, 세 군 모두 M1 과 구간이 겹쳐 "구분 안 됨"이다(평가 설계는 바꾸지 않았다).
- 현재 점수(03-31): 라벨이 있는 기준일 9개 전체로 M1 을 다시 학습해 03-31 모집단 1,569명에 점수를 매긴다. 모델은 파일로 저장하지 않는다.
  검산: 모집단 1,569 + 가입 14일 미만 제외 74 = active 이면서 탈퇴자 제외 1,643명.
- 세그먼트(03-31): 군 3 x 기간 내 구매 경험(2026-01-01 이후) 2 x 소통 공백 3(공백 4일 이상 / 공백 4일 미만 / 팔로우 없음) = 18칸.
  집계만 돌려주고 user_id 는 넣지 않는다. 20명 미만인 칸은 "해석 보류"로 표시한다. 칸의 합은 항상 대상 인원과 같다(assert).
  "공백 4일 이상" 인원이 20명 미만이면 소통 공백 축을 "해당 없음"으로 보고하고 뺀다(03-31 은 665명이라 사용).
  churn_report() 가 세그먼트 표와 군별 실제 비율 표를 항상 함께 돌려준다(군의 의미를 근거와 함께 보이기 위해).

### Day 4 (11/14) - 도구 호출 에이전트와 화면
- 에이전트는 OpenAI function calling 으로 도구 3개를 호출한다: ask_data(질문), get_churn_segments(조건), recommend_actions(세그먼트).
  루프 상한은 5단계. 도구 호출 기록(어떤 도구를, 왜, 무슨 인자로)을 응답에 포함한다.
- recommend_actions: 세그먼트 통계는 코드가 계산해서 입력으로 준다. LLM 은 세그먼트 설명, 메시지 초안, 채널(목록은 가정),
  가설, 검증 방법(지표, 비교 그룹, 기간)을 만든다.
  필요 표본 수는 코드가 계산한다 (actions.needed_per_group, 유의수준 5% 양측, 검정력 80%, 30%/50% 감소). LLM 은 표본 수를 만들지 않는다.
  금지: 효과 수치 약속, 개인 식별 정보 노출, 인과 단정. 출력은 JSON 스키마를 지킨다.
  코드가 검사하는 금지어: 효과를 약속하는 말(보장, 무조건, 반드시, 확실히, 틀림없이)은 모든 글 칸에, 내부 분류 낱말(이탈, 위험, 휴면)은
  팬에게 가는 message_draft 에만 적용한다(가설과 주의사항은 운영자가 읽는 글이라 제외). 위반하면 그 출력을 버린다.
- 화면: 기본은 Streamlit(채팅 입력, 결과 표, SQL 보기, 가정과 시도 이력 펼치기, 세그먼트 표). 시간이 남을 때만 Next.js 로 확장.
- 로그: 질문별 호출 기록을 logs/ 에 jsonl 로 저장(git 제외).

### Day 5 (11/15) - 평가와 정리, 11/16 은 버퍼(PR 과 마무리)
- 평가셋 30문항(eval/questions.yaml): 단순 집계 / 조인 / 지표 정의 필요 / 기간 해석 / 함정(탈퇴자, 닫힌 퍼널) / 답할 수 없는 질문.
  문항마다 "개발용"인지 "보류(held-out)"인지 구분을 표시한다.
  - 개발용 6문항: eval_notes.md 의 6문항. 시맨틱 레이어를 만들며 정의를 맞춘 질문이고, 이미 모델 출력을 보고 정의를 고쳤다.
  - 보류 24문항: 개발 중 한 번도 모델에 물어보지 않은 질문. 그중 3개는 거절이 정답인 질문(데이터에 없는 정보를 묻는 질문)으로 둔다.
- 보류 질문 규칙:
  - 질문과 정답 SQL 을 사람이 DBeaver 로 직접 검증해서 먼저 확정한다. 모델이 낸 SQL 이나 숫자로 정답을 만들지 않는다.
  - 확정한 뒤에는 보류 질문으로 모델을 시험하거나 그 결과를 보고 시맨틱 레이어를 고치지 않는다.
    고치게 되면 그 문항은 보류가 아니라 개발용으로 이동시키고 그 사실을 기록한다.
- 채점: 생성 SQL 의 실행 결과를 정답 SQL 의 실행 결과와 비교(행 집합 일치, 숫자는 허용 오차). 거절이 정답인 문항은 거절해야 통과.
- 리포트(eval/report.md)는 개발용 정확도와 보류 정확도를 분리해서 표기한다. 일반화 성능의 근거는 보류 정확도만 사용한다.
  (개발용 문항은 정의를 그 질문에 맞춰 고쳤으므로 높게 나오는 것이 당연하다.)
- 비교 실험(ablation): A 스키마만 / B + 값 프로파일 / C + 시맨틱 레이어 / D + 재시도와 거짓 거절 교정. 구성별 정확도, 평균 호출 수, 평균 응답 시간 표를 만든다.
  구성별 정확도는 개발용과 보류를 분리해서 표기하고, 구성 간 개선의 근거는 보류 정확도를 우선한다.
- 산출: eval/run_eval.py, eval/report.md, README 개편, 아키텍처 mermaid 도표, docs 로 쓸 "면접에서 설명할 핵심 코드 5곳".
- 데모는 공개 배포하지 않는다. 공용 크레딧이 외부 사용으로 소진될 위험이 있어서, 화면 녹화(GIF/영상)와 스크린샷으로 남긴다.

## 10. 알려진 한계
- 요약(summary)의 숫자는 코드로 검증하지 않는다. "입력에 없는 숫자를 쓰지 말 것"은 프롬프트 규칙으로만 지킨다.
  이유: 코드로 검사하면 0.1642 를 16.42% 로 바꿔 쓴 정상 요약까지 오류로 잡힌다(거짓 경보).
  그래서 정확한 숫자의 근거는 항상 rows(SQL 실행 결과)이고, summary 는 참고용 해석이다.
- 0행 결과는 재시도하지 않는다. 모델이 존재하지 않는 값으로 조건을 걸어 0행이 나온 오답은 걸러내지 못한다.
  (값 목록을 프롬프트에 넣어 예방하고, Day 5 평가셋으로 측정한다.)
- 거짓 거절 판별은 모델이 준 missing 목록에 의존한다. 모델이 missing 을 비우고 거절하면 정상 거절로 인정된다.
- assumptions 는 모델이 쓴 설명이며, SQL 과 실제로 일치하는지는 코드로 검증하지 않는다.
- 재시도, 거짓 거절 교정, 접속 오류 중단 경로는 실제 API 로 실행된 적이 없고 mock 테스트로만 검증됐다.
  (개발용 6문항이 모두 첫 시도에 성공했기 때문이다.)

Day 4 에이전트와 액션 제안의 한계 (프롬프트로만 통제되는 부분을 포함한다)
- 프롬프트로만 통제되는 부분: 코드로 강제할 수 없고 시스템 프롬프트의 규칙에만 기대는 것들이다.
  - 메시지 초안이 팬 개인의 활동 상태를 언급하지 않는 것 ("요즘 안 오셨네요" 같은 문장 금지). 금지어 검사는 낱말만 보므로 같은 뜻을 다른 말로 쓰면 통과한다.
  - 초안이 선정 방식(점수로 뽑혔다는 사실)을 드러내지 않는 것, 가설이 인과 단정이 아니라 가설 문장으로 쓰이는 것.
  - 에이전트 답이 "이탈 위험 팬(at_risk 상태)"과 "이탈 위험 순위 상위군"을 섞지 않는 것 (프롬프트의 정의 구분과 도구 설명으로 유도할 뿐이다).
- 금지어와 개인정보 검사는 낱말과 모양만 본다. 사람 이름은 잡지 못한다. 위반한 출력은 버리며, 다시 시키지 않는다.
- 숫자 점검(app/numcheck.py)은 경고 전용이다. 못 잡는 경우: 결과에 있는 숫자를 엉뚱한 대상에 붙인 경우, 모델이 직접 더하거나 뺀 값은 거짓 경보,
  "절반" 같은 글자 숫자, 정의 숫자(14, 29, 30, 10, 11)의 오용. 정확한 숫자의 근거는 항상 화면의 도구 결과 표다.
- 채널 목록(앱 푸시 / 앱 내 알림 / 이메일)은 데이터 근거가 없는 가정이며 도구 결과에 그렇게 표시한다.

Day 3 이탈 위험 점수의 한계 (모든 수치는 가정한 생성 규칙의 탐지 결과이며 인과가 아니다)
- (a) 팔로우 이력이 2026-01-01 부터만 있어서 팔로우 수와 "팔로우 없음" 표시가 날짜 대리변수가 될 수 있다
  (팔로우 없음 비율: 학습 구간 52%, 평가 구간 19%). 그래서 이 특징들은 주 모델 M1 에서 뺐다.
- (b) 평가 구간에서 소통 공백 값이 0 과 1 뿐이어서 소통 공백 특징(M3)의 효과를 검증할 수 없다.
- (c) 평가 구간 사용자 1,521명 중 1,350명이 학습 구간에도 나오므로 새로운 팬에 대한 일반화는 검증하지 못했다.
- (d) "직전 주 대비 변화"가 다른 두 활동 특징의 선형 결합(2 x 최근 7일 활동일수 - 최근 14일 활동일수)이라 M1 의 개별 계수는 해석할 수 없다.
  마지막 활동 후 일수와 최근 활동일수도 비슷한 정보라 계수가 불안정하다. 계수는 표준화 후 값이며 상관관계로만 읽는다.
  (평가 결과를 본 뒤 설계를 바꾸지 않는 규칙에 따라 M1 의 특징 구성은 그대로 두었다.)
- (e) M1 이 기준선보다 나은 것은 평균 AUC 에서만 확인됐다. 상위 100명 정밀도와 군별 실제 비율에서는 기준선과 구분되지 않았다.
- (f) 기준일당 양성이 41~69건이라 lift 구간이 넓고(M1 1.35 ~ 2.74), 기준일 간 편차도 크다(M1 1.38배 ~ 3.00배).
- (g) 분할이 한 번뿐이고 평가 기준일이 3개라, 다른 기간에서도 같은 결과가 나오는지는 알 수 없다.
- (h) 예측 확률의 최댓값이 17% 수준이라 절대 확률로는 군을 나눌 수 없고 순위로만 쓸 수 있다. 군 경계(10%, 20%)는 운영 가정이다.
- (i) 군 경계의 동점은 입력 순서로 끊는다(임의지만 항상 같은 결과). 점수가 정수인 기준선 M0 은 동점이 많아 영향이 더 크다.
- (j) 세그먼트의 소통 공백 축은 아티스트 구성 분류다. 03-31 기준 체감 소통 공백 값은 팔로우하는 아티스트 조합으로 완전히 정해진다
  (0일 = artist_002 를 팔로우, 6일 = artist_001 을 팔로우하고 artist_002 는 아님, 14일 = artist_003 만 팔로우).
  이 축은 이탈 위험 요인으로 검증되지 않았다.
- (k) 03-31 현재 점수 모델은 정답(이후 14일)이 없어 따로 평가할 수 없다. 보고하는 성능은 분할 모델 M1 의 값이다.
- (l) 가상 데이터의 90일 기간이라 계절성과 장기 효과는 알 수 없다.
- 탈퇴자 29명을 전부 제외했다. 탈퇴 시각이 기준일 이후인 사용자까지 제외하므로 약한 미래 정보 사용이다(전체의 약 1.7%).
