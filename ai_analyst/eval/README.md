# FANLOG 평가 체계 (Day 5)

Text-to-SQL(`app.text2sql.ask`)이 낸 SQL 의 실행 결과를, 사람이 검증한 정답 SQL 의 실행 결과와 비교해 정확도를 잰다.
이 폴더의 코드는 `app/` 을 고치지 않고 가져다 쓴다.

**지금 상태: 코드와 후보 질문 초안만 있다. 실제 평가는 한 번도 실행하지 않았다.** 질문이 전부 미검증(`verified: false`)이라 실제 실행은 거부된다.

## 구조

| 파일 | 하는 일 |
|---|---|
| `questions.yaml` | 평가 질문 파일. 지금은 스키마를 보여주는 예시 2문항(개발용)뿐이다 |
| `dev_drafts.yaml` | 개발용 6문항 중 나머지 4문항의 정답 SQL 초안 (같은 형식) |
| `candidates.yaml` | 보류 후보 질문 초안 40문항. 정답이 아니다 |
| `verify/reference_queries.sql` | 후보 40문항의 SQL 을 DBeaver 에서 한 문항씩 실행할 수 있게 모은 파일 |
| `verify/VERIFY_CHECKLIST.md` | 사람이 결과를 적고 verified 를 체크하는 표 |
| `questions.py` | 질문 파일의 스키마와 로더. 모르는 키를 거부하고, 미검증 문항의 실제 실행을 막는다 |
| `grading.py` | 채점. 숫자 하나(scalar), 행 집합(rows), 거절(refusal). 실패 분류. 결과에는 행 수와 요약값만 남긴다 |
| `run_eval.py` | 실행기. 기본은 dry-run |
| `ablation.py` | 비교 실험 구성 A~D. 실행 중에만 프롬프트와 재시도 횟수를 바꿨다가 되돌린다 |
| `exposure.py` | 오염 방지. 보류 질문을 처음 보인 때의 시맨틱 레이어 해시를 기록한다 |
| `report.py` | 결과 파일로 마크다운 리포트를 만든다 |
| `PROGRESS.md` | 이 초안을 만든 과정의 기록과 사람이 결정해야 할 것 |
| `results/` | 실행 결과(JSON)와 보류 질문 노출 기록이 쌓이는 곳 (실행하면 생긴다) |

## 실행 방법

모든 명령은 `ai_analyst` 폴더에서 실행한다.

### 1. 먼저 dry-run (호출 0회)

```
python -m eval.run_eval
python -m eval.run_eval --split heldout
python -m eval.run_eval --configs A,B,C,D
```

OpenAI 도 DB 도 부르지 않는다. 문항 목록, 미검증 문항 수, 구성별 예상 최대 호출 수를 보여준다.

### 2. 실제 실행 (OpenAI 호출이 일어난다)

아래가 모두 맞아야 실행된다. 하나라도 빠지면 호출 0회로 끝나고 이유를 전부 알려준다.

1. 환경변수 `FANLOG_EVAL_ALLOW=1`
2. `--confirm-calls N`: N 이 dry-run 이 알려준 "예상 최대 호출 수"와 정확히 같아야 한다
3. 고른 문항이 전부 `verified: true`
4. 환경변수 `FANLOG_MODEL` 설정

```
python -m eval.run_eval --split dev --confirm-calls 18
python -m eval.run_eval --confirm-calls 90 --max-calls 60
```

- `--max-calls` 는 하드 상한이다(주지 않으면 N). 다음 질문의 최대 호출 수를 더했을 때 상한을 넘으면 그 질문을 시작하지 않고 멈춘다.
  실행하지 못한 문항은 "호출 상한 초과"로 기록되고 리포트에서 실패로 센다.
- 정답 SQL 은 가드레일을 거쳐 읽기 전용 계정으로 실행한다(LLM 호출이 아니다). 그래서 실제 실행에는 DB 접속이 필요하다.
- 결과는 `eval/results/run_YYYYMMDD_HHMMSS.json` 에 저장된다. 행 값은 저장하지 않는다.

### 3. 리포트 (호출 0회)

```
python -m eval.report eval/results/run_YYYYMMDD_HHMMSS.json
python -m eval.report eval/results/run_YYYYMMDD_HHMMSS.json --out eval/report.md
```

## 채점 규칙

- scalar: 모델의 결과가 정확히 1행이고, 그 행의 숫자 칸 중 하나가 정답과 허용 오차 안에서 같으면 통과.
  문항의 `tolerance` 로 절대 오차(`abs`), 상대 오차(`rel`), 비율과 퍼센트를 같은 답으로 볼지(`accept_percent_or_ratio`)를 정한다.
- rows: 행 집합이 같으면 통과. 기본은 순서 무시이고, 질문이 순서를 요구하면 문항에 `ordered: true` 를 둔다.
  열 이름은 보지 않고, 열 순서는 바꿔 가며 맞춰 본다(6열까지). 열 수가 다르면 실패다.
- refusal: 모델이 거절로 끝나야 통과한다. 숫자를 내놓으면 "거절해야 하는데 답함"으로 실패한다.
- 실패 분류: 값 불일치 / 가드레일 차단 / DB 오류 / 파싱 실패 / 거짓 거절 / 거절해야 하는데 답함 / 호출 상한 초과.
  여기에 LLM 오류, 정답 SQL 실행 실패, 기타 오류를 더했다.
- 애매하면 실패로 판정한다. 그래서 형식만 다른 정답(예: 월을 `2026-01` 글자로 낸 답)이 떨어질 수 있다.

## 보류(heldout) 질문 규칙

- 정답 SQL 은 사람이 DBeaver 로 직접 실행해 확인한다. 모델이 낸 SQL 이나 숫자로 정답을 만들지 않는다.
- 확인한 뒤에는 보류 질문을 모델에 시험 삼아 물어보지 않는다. 결과를 보고 시맨틱 레이어를 고치지도 않는다.
- 고치게 되면 그 문항은 보류가 아니라 개발용으로 옮기고 그 사실을 기록한다.
- 실행기는 보류 질문을 처음 평가한 때의 `semantic_layer.yaml` sha256 을 `results/heldout_exposure.json` 에 적는다.
  그 뒤 해시가 바뀌면 리포트에 "보류 질문 노출 후 시맨틱 레이어가 바뀜: 해당 문항은 개발용으로 이동해야 함" 경고가 나온다.
  주석만 고쳐도 경고가 뜬다(놓치는 것보다 과하게 알리는 쪽을 골랐다).
- 리포트는 개발용 정확도와 보류 정확도를 따로 적는다. 일반화의 근거는 보류 정확도뿐이다.
  문항 수가 적어 구간이 넓으므로 Wilson 95% 구간을 같이 적는다.

## 비교 실험 (ablation)

| 구성 | 프롬프트 | SQL 호출 |
|---|---|---|
| A | 테이블, 컬럼, 타입만 | 1회 |
| B | A + 값 목록, 날짜 범위, 행 수 | 1회 |
| C | B + 시맨틱 레이어 (지금 앱의 프롬프트) | 1회 |
| D | 지금 앱 그대로 (재시도와 거짓 거절 교정) | 최대 3회 |

- 재시도와 거짓 거절 교정은 `ask()` 안의 같은 반복문이라 따로 떼어 볼 수 없다.
- A, B 에도 규칙 문장(`SYSTEM_RULES`)은 그대로 들어간다. 그 안에 "SEMANTIC LAYER 를 따르라"는 문장이 남아 있다.

## 호출량 안내

- 평가에서는 요약을 끄므로 질문당 SQL 생성 호출만 센다. 구성 D 는 질문당 최대 3회, A~C 는 1회다.
- 예: 30문항을 구성 D 로만 돌리면 최대 90회, A~D 를 모두 돌리면 최대 30 x (1+1+1+3) = 180회다. 실제는 첫 시도에 성공하는 만큼 줄어든다.
- 평가 호출도 `logs/` 의 오늘 합계에 들어간다(`source: eval`). 화면의 일일 한도(`FANLOG_DAILY_CALL_LIMIT`, 기본 100회)를 넘기면 그날 화면 입력이 막힌다.
  평가하는 날에는 이 환경변수를 올려 두거나 화면을 쓰지 않는다. 평가 실행기 자체는 일일 한도로 막히지 않고 `--max-calls` 로만 막힌다.
- 공용 크레딧이다. 실행 전에 매니저에게 호출량을 알리고 확인받는다(DESIGN.md 7장).

## 아직 하지 않은 것

- 실제 평가 실행(OpenAI 호출, DB 접속)은 한 번도 하지 않았다. 실행기, 채점, 리포트는 가짜 부품으로 한 테스트로만 확인했다.
- 후보 40문항의 정답 SQL 은 DB 에서 실행해 보지 않았다. 가드레일 파싱 검사만 통과했다. 결과 값을 모른다.
- `questions.yaml` 에 평가셋 30문항을 채우는 일(개발용 6 + 보류 24)은 사람의 검증이 끝난 뒤에 한다.
- 정의가 확정되지 않은 지표: W1 참여 재방문율(시맨틱 레이어 TODO), 순매출(대시보드 정의와 대조 필요).
- 에이전트(도구 호출) 경로는 평가하지 않는다. `ask()` 만 평가한다.
- 요약과 가정(assumptions)의 품질은 채점하지 않는다.
- `eval/report.md` (실제 리포트)와 README 개편, 아키텍처 도표는 만들지 않았다.
